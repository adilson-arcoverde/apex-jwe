# apex-jwe — Refactoring Design

Status: **approved 2026-09-07**; the open points of section 8 were settled in the plan and are recorded there. Implementation in progress: see section 7 for the order and section 9 for what changed during implementation.
Baseline: the seven classes under `.consolidacao/baseline/` (2026-07-23, 49 green tests, 97% coverage).

## 1. What the library does today

JSON Web Encryption (RFC 7516) in native Apex, Compact Serialization, with two key-management profiles and two content-encryption profiles:

| Header field | Supported values                                    | Where                                                                   |
| ------------ | --------------------------------------------------- | ----------------------------------------------------------------------- |
| `alg`        | `dir`, `RSA-OAEP` (SHA-1), `RSA-OAEP-256` (SHA-256) | `RSA_OAEP` via `CEKAlgorithm`                                           |
| `enc`        | `A128CBC-HS256`, `A256CBC-HS512`                    | inline in `JSONWebEncryption` (`Crypto.encrypt` + `Crypto.generateMac`) |

The refactored library adds `A192CBC-HS384` to that `enc` column: see section 9, step 8.

RSA is implemented on top of `Decimal` arithmetic (Apex has no big integer): square-and-multiply `modPow`, CRT path with fault check, Horner hex parsing. EME-OAEP and MGF1 follow RFC 8017 §7.1 and §B.2.1. Security properties already in place: fresh IV and CEK per message, algorithm pinning, uniform failure message, random-CEK substitution on unwrap failure (RFC 7516 §11.5), constant-time tag comparison, no debug output.

Measured on RSA-2048 (`Limits.getCpuTime()`, 2026-07-23): encrypt 67–134 ms, decrypt 205–263 ms.

## 2. Goals of the refactoring

1. Idiomatic Apex naming and structure, one responsibility per type.
2. Documentation that explains **why** (RFC section, threat) rather than **what**.
3. Byte-oriented internals (`Blob` / byte array) instead of hex `String` as the transport format between methods.
4. Test suite that pins behavior with published vectors, so the refactoring is provably behavior-preserving.
5. Zero Portuguese anywhere. Zero client or company references.

Non-goals: new algorithms (GCM, ECDH, JWS), changing the wire format, changing security decisions already taken.

## 3. Proposed type map

All types carry the `Jwe` prefix. A prefix is the Apex convention for libraries installed unmanaged into someone else's org: it prevents collisions with `Base64`, `ByteArray`, `Header` and friends that any org may already have.

| Baseline                                       | Proposed                       | Responsibility                                                                                                                                                                                                                         | Notes                                                                                                                                                                                                                  |
| ---------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `JSONWebEncryption`                            | `Jwe`                          | Facade: `new Jwe(JweHeader)`, `encrypt(String, JweKey)`, `decrypt(String, JweKey)`                                                                                                                                                     | Keeps the five-part assembly and the pinning / uniform-failure policy. Algorithms are configuration, keys are parameters                                                                                               |
| `JSONWebEncryption.JOSEHeader`                 | `JweHeader`                    | Immutable `alg`, `enc`, `kid`; canonical JSON through `JSONGenerator`; `encode()`, `parse()`, `hasSameAlgorithms()`                                                                                                                    | Own top-level class so consumers can build it without touching `Jwe` internals. Which algorithm names are supported is not its business: that is decided where the algorithms are built                                |
| `JSONWebEncryption.JWK`                        | `JweKey`                       | RSA and oct JWK members; `fromJson`, `fromSecretHex`; accessors returning `JweBigInt`; `modulusOctets()`, `hasPrivateExponent()`, `hasCrtParameters()`, `isSymmetric()`, `secret()`                                                    | Removes the `Map<String,String>` of hex strings passed to `decrypt`. Ignores members the library does not use                                                                                                          |
| `JSONWebEncryption.JSONWebEncryptionException` | `JweException`                 | Single exception type; configuration errors are specific, token-dependent errors are uniform                                                                                                                                           |                                                                                                                                                                                                                        |
| `CEKAlgorithm`                                 | `JweKeyEncryption` (interface) | `Blob wrap(Blob cek, JweKey key)`, `Blob unwrap(Blob wrappedKey, JweKey key)`                                                                                                                                                          | No hex strings, no `k` parameter (derived from the modulus), no `init(String)`: the hash goes to the constructor. `dir` is not an implementation — there is nothing to wrap — so the `alg` mapping stays in the facade |
| `RSA_OAEP`                                     | `JweRsaOaep`                   | RSAES-OAEP (RFC 8017 §7.1) on `JweBigInt`: `wrap`/`unwrap`, with EME-OAEP encode/decode and MGF1 internal                                                                                                                              | No alias for the old name: nothing outside this repository depends on it (decided 2026-09-07)                                                                                                                          |
| — (inline)                                     | `JweAesCbcHmac`                | AEAD composition of RFC 7518 §5.2: `encrypt(cek, iv, aad, plaintext)` returning `Encrypted(ciphertext, tag)`, `decrypt(cek, iv, aad, encrypted)`; MAC key / ENC key split; AL computation; tag truncation; `keyOctets()`, `ivOctets()` | Extraction is what makes the RFC 7518 Appendix B vectors testable                                                                                                                                                      |
| — (inline helpers)                             | `JweBase64Url`                 | `encode(Blob)`, `decode(String)` with strict alphabet                                                                                                                                                                                  | Three methods, tested against RFC 4648 §10 vectors                                                                                                                                                                     |
| `ByteBlob`                                     | `JweBytes`                     | Immutable byte array over `Blob`: `concat`, `xor`, `slice`, `indexOf`, `random`, `zeros`, `i2osp4`, `equalsConstantTime`, `toBlob`, `toHex`                                                                                            | Rewritten from scratch (origin of `ByteBlob` not located, see THIRD_PARTY_NOTICES)                                                                                                                                     |
| —                                              | `JweBigInt`                    | `modPow`, `modPowCrt`, `mod`, `isLessThan`, `fromHex`/`fromBytes`/`toHex`/`toBlob` over `Decimal`                                                                                                                                      | Extracted from `RSA_OAEP` so the arithmetic is testable on its own (Fermat, small primes, known RSA-512 vector)                                                                                                        |

Ten types instead of four. Each is small and has a single reason to change.

## 4. Public API (proposed)

```apex
// The header is configuration: it decides what this instance produces and accepts. The key is
// a parameter, because it belongs to the message, and because where it is stored is the
// caller's decision, not the library's.
Jwe jwe = new Jwe(new JweHeader('RSA-OAEP-256', 'A256CBC-HS512').withKeyId('2026-09'));

// Encrypt with a public JWK (n and e), decrypt with a private one (n, e, d; the CRT members
// are used when present).
String token = jwe.encrypt('{"sub":"..."}', JweKey.fromJson(publicJwkJson));
String payload = jwe.decrypt(token, JweKey.fromJson(privateJwkJson));

// Direct encryption. A shared key is a JWK of type oct (RFC 7518 §6.4); fromSecretHex is the
// shortcut for the hex form a pre-shared secret is usually configured in.
Jwe shared = new Jwe(new JweHeader('dir', 'A256CBC-HS512'));
String direct = shared.encrypt('{"sub":"..."}', JweKey.fromSecretHex(sharedKeyHex));
```

Behavioral contract preserved from the baseline:

- The configured header pins `alg`/`enc`; a token whose header differs fails with the uniform message.
- The key is a parameter of `encrypt` and `decrypt`, never held by the instance, so one configured instance serves many keys and the library never decides how a key is stored.
- Every token-dependent failure raises `JweException('JWE decryption failed')`. Configuration failures raise `JweException` with a specific message.
- IV and CEK are fresh per `encrypt`. The test-only IV injection survives as `@TestVisible` and is consumed after one use.
- Output alphabet is strict Base64URL, no padding. RSA ciphertext is exactly `k` octets.

Breaking changes versus the baseline (acceptable: this is the first public release):

- Class and method names. The `RSA_OAEP` name is dropped outright, with no deprecated shim.
- `CEKAlgorithm` replaced by `JweKeyEncryption` with a byte-oriented signature.
- `setProtectedHeader` replaced by the constructor; `setCEKAlgorithmKey` and `setContentEncryptionKeySecret` replaced by the key parameter of `encrypt` and `decrypt`.

## 5. Behavior freeze: test vectors before any code change

Step 0 of the implementation. Every vector is stored as a constant in a dedicated test class and asserted against the **baseline** first, then against the refactored code.

| Source                                                                                                       | What it pins                                                     | Class                                                                                    |
| ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| RFC 8017 / PKCS#1 v2.1 classic EME-OAEP vector (message, seed, EM for SHA-1)                                 | OAEP encode/decode                                               | already in baseline                                                                      |
| Baseline SHA-256 EME-OAEP vector and MGF1 vector                                                             | MGF1, OAEP-256                                                   | already in baseline                                                                      |
| **RFC 7518 Appendix B.1, B.2, B.3** (K, P, IV, A → E, T)                                                     | `JweAesCbcHmac` for A128CBC-HS256, A192CBC-HS384*, A256CBC-HS512 | new — the extraction of `JweAesCbcHmac` is what makes these testable. All three now pass |
| **RFC 4648 §10** Base64 vectors adapted to Base64URL                                                         | `JweBase64Url`                                                   | new                                                                                      |
| Baseline interop tokens generated with Node `crypto` (dir and RSA-OAEP)                                      | end-to-end decrypt of externally produced tokens                 | already in baseline                                                                      |
| **New interop tokens generated with `jose` (Node)** for RSA-OAEP-256 + A256CBC-HS512 and dir + A128CBC-HS256 | closes the matrix                                                | new, generated once by a script under `scripts/` and pasted as constants                 |
| Small-modulus RSA vector (RSA-512 test key, known c for known m)                                             | `JweBigInt.modPow` and CRT path independently of OAEP            | new                                                                                      |

\* A192CBC-HS384 was assumed unsupported when this section was written, on the belief that Apex had no AES-192. That belief was wrong (section 9, step 8), and B.2 is now a round-trip vector like the other two.

## 6. Documentation deliverables

- ApexDoc on every public type and member: `@description`, `@param`, `@return`, `@throws`, `@see <RFC URL#section>`.
- Inline comments only where the RFC or a security decision needs explaining. Example: why the CEK is replaced by random bytes on unwrap failure; why the tag is compared with an accumulator.
- `README.md`: problem statement, supported matrix, 10-line example, governor-limit guidance, performance table, related work (`alex-shekhter/apex-crypto-rsa-oaep-sha256`, 2023), license.
- `docs/ARCHITECTURE.md`: the compact-serialization pipeline with a diagram, the type map above, the `Decimal` big-int trade-off.
- `docs/SECURITY.md`: threat model, key storage guidance (Protected Custom Metadata or Named Credential; never in code), what the library does not defend against, reporting channel.
- `CHANGELOG.md`, `THIRD_PARTY_NOTICES.md`, `LICENSE` (PolyForm Noncommercial 1.0.0).

## 7. Implementation order

Each step ends with the full suite green on the validation org.

1. Test vectors (section 5) against the baseline. Commit `test: freeze behavior with RFC and interop vectors`.
2. `JweException` + `JweBytes` (rewrite) + `JweBase64Url` + `JweBigInt` with their tests. Baseline classes still in place, untouched. **Done 2026-09-07**: 94 green tests on the validation org (49 baseline + 45 new), 100% coverage on the three new classes.
3. `JweKey` + `JweRsaOaep` on top of step 2. Cross-check: same EM as `RSA_OAEP` for the fixed-seed vectors, and ciphertext interoperable with the baseline in both directions. **Done 2026-09-07**: 125 green tests on the validation org, 100% coverage on every new class.
4. `JweAesCbcHmac` + RFC 7518 Appendix B vectors. **Done 2026-09-07**: 138 green tests on the validation org, B.1 and B.3 reproduced octet for octet, B.2 asserted as unsupported.
5. `JweHeader` and `JweKeyEncryption` (`JweKey` and `JweException` were brought forward, see section 9). **Done 2026-09-07**: 152 green tests on the validation org; the canonical header serialization is pinned against headers produced by `jose`.
6. `Jwe` facade. Interop tokens must decrypt. Tokens produced by `Jwe` must decrypt with baseline `JSONWebEncryption` and vice versa (same wire format). **Done 2026-09-07**: 176 green tests on the validation org, the four external tokens decrypt, and both crossings with the baseline hold for `dir` and `RSA-OAEP-256`.
7. Delete baseline classes, with no `RSA_OAEP` shim. Run the Portuguese and identity greps. Code Analyzer clean. **Done 2026-09-07**: seven baseline classes removed, 121 green tests, 100% org-wide coverage, Code Analyzer clean under `code-analyzer.yml`.
8. Documentation (section 6). Publish.

## 8. Open points for the author

1. **Prefix `Jwe`** (recommended) versus no prefix. Decide once; renaming later is a breaking change. **Settled: `Jwe`.**
2. **Validation org.** **Settled:** a personal Developer Edition, authenticated locally. The baseline and every step since deploy and run their tests there. Which org it is stays out of this repository.
3. **`RSA_OAEP` shim**: keep for one version, or drop since no external consumer exists yet? Recommendation: drop; nobody depends on the public name. **Settled: dropped.**
4. **Test JWK**: the baseline embeds a throwaway RSA-2048 key pair as constants. Keep (simplest, already documented as throwaway) or generate per test run with an external tool? Recommendation: keep, with a `// Throwaway test key. Never used outside this suite.` comment. **Settled: kept, with that comment.**

## 9. Amendments during implementation

Deviations from the design above, decided while implementing and kept here so the document stays
the record of what was built.

| Step | Amendment                                                                                                                                                 | Reason                                                                                                                                                                                                                                                                                                                                            |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2    | `JweException` created in step 2 instead of step 5                                                                                                        | The primitives of step 2 have to reject bad input with the library's own exception; the alternative was `InvalidParameterValueException` (as the baseline used) in code that would be rewritten again in step 5                                                                                                                                   |
| 2    | `JweBytes.equalsConstantTime` added to the type map                                                                                                       | The tag comparison of RFC 7518 §5.2.2.2 is an operation on byte strings, and `JweAesCbcHmac` (step 4) is its only consumer; keeping it in `JweBytes` means it is tested against byte strings directly                                                                                                                                             |
| 2    | `JweBytes.random` draws from `Crypto.generateAesKey` instead of `Crypto.getRandomInteger`                                                                 | `getRandomInteger` is capped at 2^31-1, so the baseline left the top bit of every fourth octet at zero. The wire format does not change; the OAEP seed, CEK and IV gain the 8 bits per 32 octets the cap was costing                                                                                                                              |
| 2    | `JweBigInt` rejects what the baseline tolerated: invalid hex digits, a negative modulus, and a value wider than the requested octet length                | The baseline returned `-1` from `modPow` and let `leftPad` emit a ciphertext longer than the modulus. Both are unreachable from a correct caller and silently corrupt output when reached                                                                                                                                                         |
| 2    | `JweBytes.ofValues` and `JweBytes.concat` reject null elements, which `ByteBlob` skipped                                                                  | Skipping a null part silently shortens a byte string, which in this library means a wrong mask or a wrong AAD                                                                                                                                                                                                                                     |
| 3    | `JweKey` created in step 3 instead of step 5                                                                                                              | The RSA layer needs a key, and the only alternative was a signature taking loose modulus and exponent parameters that step 5 would immediately replace                                                                                                                                                                                            |
| 3    | The OAEP label is dropped rather than kept as a parameter                                                                                                 | RFC 7518 §4.3 defines no label for RSA-OAEP in JOSE, so L is always the empty string. The hash of the empty label is computed once per instance; a parameter that can only hold one value is not an API                                                                                                                                           |
| 3    | EME-OAEP `encode`/`decode` and `mgf1` are private and `@TestVisible`, where the baseline had them public                                                  | The published surface is `wrap`/`unwrap`; the padding is not something a JWE consumer composes. The RFC 8017 vectors reach them through test visibility, which they already needed for the fixed seed                                                                                                                                             |
| 3    | `JweBigInt.isLessThan` added                                                                                                                              | RFC 8017 §7.1.2 step 1.b requires rejecting a ciphertext representative outside 0..n-1 before the private key operation, which the baseline never checked                                                                                                                                                                                         |
| 3    | `unwrap` rejects a ciphertext whose length is not the modulus length                                                                                      | Same RFC step. The baseline accepted any length and let the arithmetic absorb it                                                                                                                                                                                                                                                                  |
| 3    | New test-only class `JweTestKeys`                                                                                                                         | Three suites need the same throwaway RSA-2048 JWK; the baseline pasted it into each one                                                                                                                                                                                                                                                           |
| 4    | `JweAesCbcHmac` takes the whole CEK and splits it, instead of receiving the MAC key and the encryption key separately as the baseline did                 | RFC 7518 §5.2.2.1 defines the CEK as the two keys concatenated. Splitting it in one place removes the half-key juggling the facade used to do, and it is what let the Appendix B vectors be fed in as published                                                                                                                                   |
| 4    | The AAD is a `Blob`, not the encoded header string                                                                                                        | AL is defined over the octets of the AAD. Taking octets is both RFC-faithful and what makes the Appendix B vectors, whose AAD is not a JOSE header, expressible                                                                                                                                                                                   |
| 4    | On decryption an initialization vector of the wrong length reports the uniform failure, while on encryption it reports a specific one                     | The IV of a decryption comes from the token and is attacker controlled; the IV of an encryption comes from the caller                                                                                                                                                                                                                             |
| 4    | No `try` around `Crypto.encrypt`                                                                                                                          | With the key and IV lengths already checked, nothing catchable remains: a failure there would be a governor limit, which Apex does not allow a library to catch. The baseline wrapped it in an `Unexpected Error` message that could never be produced                                                                                            |
| 5    | The header is serialized with `JSONGenerator`, not with a string template                                                                                 | The baseline built the JSON by replacing placeholders, so a `kid` carrying a double quote could close the string and inject a second `alg` member into the header it authenticates. A generator escapes values                                                                                                                                    |
| 5    | Algorithm pinning compares with `String.equals`, not with `!=`                                                                                            | Apex string `==` is case insensitive, so the baseline accepted a token whose header said `a256cbc-hs512`. RFC 7515 §4.1.1 makes header values case sensitive. Stricter than the frozen baseline, deliberately                                                                                                                                     |
| 5    | `JweHeader.parse` rejects `crit` and `zip`                                                                                                                | The baseline ignored both. `crit` exists precisely to say that ignoring a member is not acceptable (RFC 7516 §5.2 step 5), and `zip` would hand back a plaintext still deflated                                                                                                                                                                   |
| 5    | No factory type for `alg`                                                                                                                                 | With `dir` outside the interface, the mapping from `alg` to an implementation has one consumer, the facade, and lives there                                                                                                                                                                                                                       |
| 6    | A `dir` token whose encrypted key part is not empty is rejected                                                                                           | RFC 7518 §4.5 makes that part the empty octet sequence for direct encryption. The baseline ignored the part entirely in `dir` mode                                                                                                                                                                                                                |
| 6    | The facade converts the content encryption failure into its own uniform message                                                                           | `JweAesCbcHmac` reports `Content decryption failed`, which is uniform within that class; the token-facing contract is one message for the whole library                                                                                                                                                                                           |
| 6    | Test data moved into `JweTestKeys` and `JweTestTokens`                                                                                                    | The four external tokens are now asserted twice, against the baseline and against the facade, and a vector kept in two places is a vector that can drift                                                                                                                                                                                          |
| 7    | The two older interop tokens were migrated instead of deleted with `JSONWebEncryptionTest`                                                                | They were produced with the Node `crypto` module rather than jose. Two independent producers of the same wire format is worth keeping                                                                                                                                                                                                             |
| 7    | `Jwe` has two constructors instead of one taking four arguments, and the private one takes the shared key first                                           | Four arguments tripped `ExcessiveParameterList`, and the obvious fix, two overloads each taking a header and one nullable object, would have made `new Jwe(header, null)` ambiguous for a caller                                                                                                                                                  |
| 7    | `Jwe.decrypt`, `JweKey.fromJson`, `JweRsaOaep.unwrap` and `JweRsaOaep.decode` were split                                                                  | Each had grown to hold two steps: reading a token and checking it, reading members and validating them, the RSA primitive and the padding. The linter noticed; the reading is better for it                                                                                                                                                       |
| 7    | The assertions of `JweTest` moved from a helper to the call sites                                                                                         | `ApexUnitTestClassShouldHaveAsserts` was right that a test whose only statement is a helper call does not show what it asserts. `failureOf` now returns the message and each test asserts it                                                                                                                                                      |
| 8    | The key moved from the constructor to the arguments of `encrypt` and `decrypt`, and `Jwe.direct` was dropped                                              | Author's decision, 2026-09-07, on the grounds that a community library must not have an opinion on where a key is stored. It also makes one configured instance serve many recipients, and keeps key material out of a long lived object                                                                                                          |
| 8    | `A192CBC-HS384` is supported, and RFC 7518 Appendix B.2 became a round-trip vector                                                                        | The claim in section 5 that Apex has no AES-192 was never verified. It is false: `Crypto.encrypt` takes `AES192` and `Crypto.generateMac` takes `hmacSHA384`, both confirmed on the validation org. Supporting it cost one entry in the profile map, and the published vector that had been kept as a negative case now proves it octet for octet |
| 8    | `JweKey` gained `kty` oct support and `fromSecretHex`                                                                                                     | With keys as parameters, `dir` needs a key object like every other algorithm. RFC 7518 §6.4 already defines what a shared key looks like in JOSE, so there was no new format to invent                                                                                                                                                            |
| 7    | `code-analyzer.yml` and `config/pmd-ruleset.xml` were added, turning off `ApexUnitTestClassShouldHaveRunAs` and raising the class level complexity totals | This library has no sharing-sensitive code for `runAs` to establish, and its design is deliberately many small methods, which a class total penalizes. The method level limits stay live: at 14 and 16 nothing exceeds them, and lowering them to 5 produces 30 findings, so the check is not a no-op                                             |
